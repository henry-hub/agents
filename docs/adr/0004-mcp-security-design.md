# ADR-0004: MCP Server 认证与安全设计（基线）

- **状态**：已采纳
- **日期**：2026-08-22
- **决策者**：IHub 团队

## 背景

进度审计（2026-08-22）确认 B4「认证安全设计」零产出：mcp-server 无任何传输认证，
对外暴露即等于暴露无认证服务。行业现状：安全是企业采用 MCP 的 #1 阻碍
（MCP 2026 规格 RC 引入集中授权方向，但尚未定稿，见战略重评估文档第四节）。

P2 的 mcp-server 提供三类工具：

| 工具组 | 能力 | 风险 |
|--------|------|------|
| CatalogTools | 能力目录查询（只读） | 低：数据公开 |
| MigrateTools | 项目路径扫描分析 | 中：可读取服务器本机文件系统路径 |
| ModuleTools | 模块描述符查询（只读） | 低 |

## 决策

### D1：传输认证采用 Bearer 静态令牌（最小基线）

- 配置 `ihub.mcp.security.token` 后，所有请求必须携带
  `Authorization: Bearer <token>`，否则返回 401
- 未配置令牌时为**开发模式**：放行所有请求并打印 WARN 日志（启动时明确提示）
- 健康检查路径（`/actuator/health`）豁免，便于探活

**理由**：零外部依赖、可立即落地；OAuth 2.1 / 集中授权等方案待
2026-07-28 MCP 规格定稿后再演进（与战略文档调整 4 一致：RC 观望，定稿后适配）。

### D2：工具级授权暂不分层

当前工具均为查询/分析类（无写操作），统一认证即可；
未来引入写操作工具（如触发迁移执行）时，按 tool scope 细分授权。

### D3：Catalog 数据源信任边界

- 默认从 classpath 加载打包进 jar 的 catalog.json（构建期可信）
- `file:` 路径覆盖仅限部署运维人员可控的配置项，不暴露为运行时接口
- ProjectScanner 分析的项目路径由调用方传入，限定为只读扫描（不做文件写操作）

## 后果

- **正面**：生产部署有最小认证门槛；配置缺省时开发体验不受影响
- **负面**：静态令牌需自行轮换分发，无用户级审计；
  待 MCP 授权规格定稿后需二次演进（令牌方案 → 标准化授权）
- **跟进项**：规格定稿后评估 OAuth 2.1 / Resource Server 模式替换静态令牌
